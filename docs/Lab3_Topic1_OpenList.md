# ЛР №3. Тема для защиты №1: список O в алгоритмах эвристического поиска

> Список O в алгоритмах эвристического поиска: требуемый абстрактный тип данных и способы его реализации на основе конкретных структур данных.

## 1. Роль списка O

Список O (open) хранит **обнаруженные, но ещё не раскрытые** узлы. На каждой итерации алгоритм
извлекает из O один узел, раскрывает его (генерирует потомков) и добавляет новых потомков в O.
То, *какой* узел извлекается, полностью определяет стратегию поиска:

| Алгоритм | Какой узел извлекается из O | Требуемый АТД |
|----------|-----------------------------|---------------|
| Поиск в глубину | добавленный последним | стек (LIFO) |
| Поиск в ширину | добавленный раньше всех | очередь (FIFO) |
| Поиск равных цен (Дейкстра), A*, жадный поиск | с наименьшим значением оценки | **очередь с приоритетом** |

Для A* приоритет узла — функция оценки **f(n) = g(n) + h(n)**: чем меньше f, тем раньше узел
извлекается. Значит, в алгоритмах эвристического поиска список O должен быть **очередью с приоритетом**
(в данном случае — с извлечением минимума, min-priority queue).

## 2. Абстрактный тип данных «очередь с приоритетом»

Минимальный набор операций (интерфейс `IOpenList` в `OpenList.cs`):

| Операция | Смысл |
|----------|-------|
| `Insert(узел, f)` | добавить узел с приоритетом f |
| `ExtractMin()` | извлечь и удалить узел с наименьшим f |
| `Count` / `IsEmpty` | размер, проверка на пустоту |

Дополнительно в общем случае нужны:

* **Обновление приоритета** (`DecreaseKey`) — когда к уже лежащему в O состоянию найден более короткий путь,
  и его g, а значит и f, уменьшились;
* **Поиск узла/проверка принадлежности** — чтобы не дублировать состояние, уже находящееся в O.

В проекте эти две возможности вынесены из списка O наружу: проверка принадлежности выполняется
хэш-таблицей «состояние → узел» (`AStarSolver`), а обновление приоритета делается **ленивым удалением**:
в O просто добавляется новая запись с меньшим f, а устаревшая запись остаётся и пропускается при
извлечении (у неё g не совпадает с актуальным g узла). Поэтому интерфейс списка O остаётся минимальным.

### Порядок при равных f

Приоритет в проекте — пара (f, −g): при равных f раньше извлекается узел с **большим g**, т.е. более глубокий
и потому, как правило, более близкий к цели. Это не влияет на оптимальность, но уменьшает число раскрытых узлов.

## 3. Способы реализации и их стоимость

Пусть n — число записей в O.

| Структура данных | Insert | ExtractMin | Комментарий |
|------------------|--------|------------|-------------|
| Неупорядоченный список/массив | O(1) | O(n) | при извлечении просматривается весь список |
| Упорядоченный список/массив | O(n) (O(log n) на поиск места + сдвиг) | O(1) | минимум всегда на краю |
| **Двоичная куча** | O(log n) | O(log n) | универсальный выбор, нет «плохого» случая |
| Сбалансированное дерево поиска (красно-чёрное, AVL), `SortedSet` | O(log n) | O(log n) | поддерживает и удаление произвольного узла |
| Корзины по значению f (bucket queue) | O(1) | O(1) амортизированно | годится, если f — небольшое целое |
| Фибоначчиева куча (и др.) | O(1) амортиз. | O(log n) амортиз. | выгодна при очень частом `DecreaseKey`, на практике сложнее и медленнее |

### Реализации в проекте (`OpenList.cs`)

1. `BinaryHeapOpenList` — двоичная куча на массиве (основная). Потомки узла i лежат в ячейках 2i+1 и 2i+2;
   вставка «просеивает вверх», извлечение — «вниз».
2. `SortedArrayOpenList` — массив, упорядоченный по убыванию приоритета; минимум берётся с конца,
   место вставки ищется двоичным поиском.
3. `UnsortedOpenList` — обычный список, минимум ищется линейным просмотром.
4. `BucketOpenList` — для каждого значения f отдельный стек; указатель минимальной непустой корзины
   только движется вперёд, поэтому обе операции в среднем O(1). Применимо, потому что в этой
   головоломке стоимость хода равна 1, а значит f — небольшое целое число.

В программе реализацию списка O можно выбрать в выпадающем списке, а кнопка «Сравнить алгоритмы»
запускает один и тот же поиск A* со всеми четырьмя реализациями и показывает время (число раскрытых
узлов при этом одинаково, различается только стоимость операций над O).

## 4. Как выбрать реализацию

* Число операций `Insert` в A* заметно больше числа `ExtractMin` (из каждого раскрытого узла в O
  попадает до 16 потомков), поэтому структура с дорогим `Insert` (упорядоченный массив) проигрывает куче
  по мере роста O, а структура с дорогим `ExtractMin` (неупорядоченный список) — ещё сильнее, т.к. O велик.
* **Двоичная куча** — компромисс «по умолчанию»: обе операции за O(log n), простая реализация, без
  зависимости от свойств функции f.
* **Корзины** быстрее кучи, когда f целочисленна и принимает мало значений (как здесь), но неприменимы
  при вещественных или очень разбросанных f.
* Если при раскрытии часто находятся более короткие пути к уже известным состояниям, полезна структура с
  эффективным `DecreaseKey` (куча с индексами/фибоначчиева) или ленивое удаление, как в проекте — ценой того,
  что O временно содержит устаревшие записи.
* В алгоритмах SMA* дополнительно нужна операция удаления **худшего** узла (с наибольшим f) — тогда
  удобна двусторонняя очередь с приоритетом или сбалансированное дерево.

## 5. Связь с остальными списками

Список C (закрытые, уже раскрытые узлы) и множество обнаруженных состояний реализуются хэш-таблицей:
по состоянию нужно быстро (в среднем за O(1)) узнать, встречалось ли оно и каково лучшее известное g.
Размер списков O и C даёт оценку расхода памяти алгоритмом: в статистике программы это «макс. размер
списка O» и «макс. |O| + |C|».
